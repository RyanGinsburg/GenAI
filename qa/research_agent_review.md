# research_agent.py manual review

Generated by `qa/research_agent_review.py`. For each club below: open the website link yourself, check whether the extracted fields are actually correct (and that nothing true on the site was missed), and fill in the **Verified?** row.

**Note: this file is regenerated from scratch every time the script runs, which wipes any Verified?/Notes filled in by hand.** The history below records what's been checked and fixed across runs so it isn't lost each time.

**2026-09-03, original manual review:** all 20 sites opened live and checked field by field. Found two bugs: (1) coffee chat links were being dropped because `_page_text()` discarded all `<a href>` URLs, keeping only visible link text, and (2) Cornell Wall Street Club came back entirely `not_found` despite having real recruiting data on its `/recruitment.html` page.

**2026-09-03, first two fixes confirmed against the live API:** `_page_text()` now preserves each link's absolute URL next to its anchor text, and the prompt was told not to let a vague "details TBD" placeholder elsewhere on a page override concrete data that's also present (root cause of the Wall Street Club miss - not JS rendering as first suspected, see the git history for the full trace). Also fixed in the same pass: `_find_secondary_url` restricted to same-domain links, since it had followed an off-domain LinkedIn profile for Blockchain at Cornell. Result: Cornell Wall Street Club now returns real data, and all 7 previously-missing coffee chat links are populated (Cornell Business Analytics Club, Cornell XR, 180 Degrees Consulting, Cornell FinTech Club, AppDev at Cornell, Cornell Wall Street Club, Investment Banking Club).

**2026-09-03, third fix, same day:** a user review of this file pushed back that the high `not_found` rate looked less like clubs genuinely not posting info and more like applications living behind a link the scraper wasn't finding. That turned out to be correct for several clubs: `_find_secondary_url` picked the *first* keyword-matching nav link in document order, not the *best* one, so a page with both a generic "Contact"/"Events" link and the club's actual "Apply" page would often follow the generic one (whichever happened to appear first in the HTML) and miss the real recruiting page entirely. Fixed by reordering `SECONDARY_LINK_KEYWORDS` by priority (apply/recruit/join before events/contact) and having `_find_secondary_url` scan every matching link on the page and pick the highest-priority one, instead of stopping at the first match. Confirmed against the live API: **4 more clubs flipped from `not_found` to real hits** - Cornell Real Estate Club, Cornell Consulting Club, Cornell Algo Trading Club, and Quant Fund at Cornell (see their sections below) - bringing the total to 11/20 real hits (up from 7/20). One related, now-documented limitation: Blockchain at Cornell's "Apply Now" button is not a real `<a href>` at all (it's a client-side Framer component with a JS click handler), so there's no static URL for `_find_secondary_url` to find even now - that would need actual browser/JS rendering to resolve, which is out of scope for the current `requests`/`BeautifulSoup` approach.

The checkboxes below are unfilled (the script always regenerates the file fresh) but the values themselves were cross-checked against manual live-site findings rather than re-verified field-by-field from scratch each run.

**Observed but not a code bug:** Cornell Data Strategy Club's `not_found`/error result is flaky across runs - its homepage's raw HTML sometimes contains only the string "Cornell Data Strategy" (a near-empty client-rendered shell) and sometimes contains fuller pre-rendered content including a "Recruitment" page with real (and partly stale, "Fall 2024") text. On one run where the fuller content came through, the model returned malformed non-JSON output instead of extracting from it, and the pipeline correctly fell back to `not_found` with an error message rather than crashing or fabricating a result - exactly the safe behavior CLAUDE.md's hard constraint asks for. Re-running against the same URL a moment later got the near-empty shell again and a clean `not_found`. Left as-is since the site itself is the inconsistent part, not the code.
